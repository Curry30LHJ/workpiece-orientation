# 动态正反面模板数量设计

## 1. 背景与目标

当前工件库把正面和反面模板固定为各 5 张。该限制会造成两类问题：一方面少量样本无法快速验证，另一方面当某一面需要更多视角或更多遮挡变化样本时，用户选择的图片无法全部进入缓存。

本变更将模板数量改为“每面任意正整数、正反面数量可不同”，并保证选中的每一张有效图片都会写入工件库并参与预测。旧版本已经建立的 5+5 工件库不需要迁移即可恢复。

## 2. 范围与不变项

### 2.1 本次包含

- Python 后端的建库校验、缓存生成、预测遍历和工件库恢复。
- TCP 建库请求的参数校验，以及建库过程进度事件。
- Qt 模板多选、数量提示、低样本提醒、建库进度/耗时和完成结果。
- 覆盖等数量与不等数量模板的单元测试、协议测试、Qt 测试和旧库恢复测试。
- 建库与预测耗时的数量扩展测量。

### 2.2 本次不包含

- 不修改 PP-ShiTuV2、ALIKED、LightGlue、局部/全局融合阈值或特征提取模型。
- 不增加训练、微调或新模型依赖。
- 不改变已有的图像预处理、候选评分和最终判定逻辑；仅改变候选模板集合的数量。
- 离线基准脚本中用于固定对比实验的样本数量可以继续使用 5 张，但生产建库流程不再包含“正好 5 张”的限制或文案。

## 3. 数据模型与兼容性

### 3.1 模板缓存

`TemplateCache` 按标签保存完整集合：

- `global_vectors["front"]` 和 `global_vectors["back"]` 的第一维分别等于正面、反面实际模板数；
- `local_features["front"]` 和 `local_features["back"]` 分别保存同样数量的局部特征；
- 预测时对每个标签的全部候选执行现有全局/局部评分，取现有规则下的最佳结果；不使用固定下标、固定循环次数或固定 5 张假设。

### 3.2 manifest

新建库的 `manifest.json` 增加实际数量字段：

```json
{
  "schema_version": 1,
  "id": "...",
  "name": "...",
  "labels": {"0": "front", "1": "back"},
  "template_counts": {"front": 5, "back": 12},
  "created_at": "..."
}
```

恢复时：

1. 如果存在 `template_counts`，校验它与磁盘上两个标签目录中的实际文件数一致；不一致视为损坏并拒绝该库。
2. 如果没有 `template_counts`，按旧版本行为从 `0/`、`1/` 目录枚举并校验图片，数量由目录内容推导。因此旧版 5+5 库继续兼容，且不把 5 当作新规则。

模板文件按用户选择顺序逐一复制；不按数量切片、不截断、不丢弃。

## 4. 校验规则

建库前后端均执行必要校验，后端是最终可信边界：

- 正面和反面列表都必须是列表，且长度均为正整数；两面数量可以不同；不设置最大数量。
- 每个元素必须是字符串路径；任何非字符串元素直接拒绝请求，不再静默过滤。
- 每个路径必须指向支持的图片扩展名、普通文件且可被图像读取器读取。
- 同一面的重复路径拒绝；正面与反面之间的重复路径也拒绝。路径比较使用解析后的规范化路径并忽略 Windows 大小写差异。
- 空列表、无效路径、不可读图片、重复图片返回明确错误，且不创建半成品工件库。
- 模板数量过多只影响耗时提示，不构成拒绝条件；所有通过校验的图片都进入缓存。
- Qt 在任一面少于 3 张时显示黄色提示，但仍允许用户建库；数量显示使用实际值，不出现“/5”或“正好 5 张”。

## 5. 建库进度协议

为了让 Qt 能显示真实进度，建库请求保留现有最终响应，同时允许在最终响应前发送同一 `request_id` 的进度事件：

```json
{
  "version": 1,
  "request_id": "...",
  "event": "progress",
  "command": "register",
  "progress": {
    "phase": "features",
    "label": "front",
    "completed": 7,
    "total": 17,
    "elapsed_ms": 842
  }
}
```

约定：

- `total` 为正反面模板数之和，`completed` 单调递增；校验、复制和特征缓存阶段至少发送开始/完成状态，特征处理阶段按图片发送进度。
- `BackendClient` 收到进度事件时只发出进度信号，不清除待处理请求、不停止超时计时器；收到最终成功或失败响应后才结束请求。
- 旧客户端只等待最终响应即可继续工作，因为最终响应格式保持兼容，并额外返回 `template_counts` 和 `elapsed_ms`。
- 进度发送失败不改变建库结果；连接断开时后端继续按现有事务规则清理或提交，Qt 显示连接错误。

最终成功响应包含：

```json
{
  "ok": true,
  "workpiece": {"id": "...", "name": "..."},
  "template_counts": {"front": 5, "back": 12},
  "elapsed_ms": 1234
}
```

## 6. Python 后端设计

### 6.1 `OrientationClassifier`

移除固定数量常量和 `len(...) == 5` 检查。`build_template_cache` 接收两个非空序列和可选进度回调，按序读取每张图片、提取全局向量与局部特征，并在每张图片完成后回调。已有评分函数、阈值和设备选择保持不变。

### 6.2 `WorkpieceLibrary`

将“正好 5 张”校验改为正整数校验，保留全部路径校验和跨面重复校验。事务暂存目录复制所有模板，manifest 写入实际数量，缓存构建失败时回滚。恢复流程使用第 3 节的 manifest 兼容规则。

### 6.3 TCP 服务

注册请求不再使用列表过滤表达式；列表中出现非字符串即返回 `INVALID_REQUEST`。dispatcher 和 TCP server 传递可选进度回调，最终响应附带实际数量与耗时。其它命令、模型和阈值不变。

## 7. Qt 界面设计

- 两个模板按钮均使用 `QFileDialog::getOpenFileNames`，不限制选择数量；对话框标题不含固定数字。
- 状态文本显示“正面已选择 N 张、反面已选择 M 张”，并在少于 3 张时显示提醒。
- 点击建库后禁用重复提交，显示总数、当前阶段、`QProgressBar` 和已耗时；进度来自 TCP 事件，耗时使用界面侧单调计时器实时刷新。
- 成功后显示后端返回的实际正面/反面数量和总耗时；失败后停止计时并保留可重试状态。
- 选择路径时不做静默去重；重复图片由校验流程明确提示并阻止建库。

## 8. 测试计划与验收标准

### 8.1 Python 单元/集成测试

至少覆盖：

| 场景 | 期望 |
| --- | --- |
| 1+1 | 建库成功，manifest/cache 为 1、1，预测遍历两张模板 |
| 5+10 | 建库成功，数量不相等且全部文件存在并参与预测 |
| 10+15 | 建库成功，恢复后数量仍为 10、15 |
| 31+31（或任一侧超过 30） | 只产生性能提醒，不拒绝，不截断 |
| 空列表 | 拒绝，库目录不落盘 |
| 非字符串/不存在/不可读图片 | 拒绝，不静默忽略 |
| 同面重复、跨面重复 | 拒绝 |
| 旧版无 `template_counts` 的 5+5 manifest | 恢复成功 |
| 预测缓存数量 | 只依赖实际集合长度，不依赖常量 5 |
| 进度事件 | `completed` 单调递增，最终响应包含数量和耗时 |

### 8.2 Qt 测试

验证任意多选、正反面不等数量显示、少量提示、进度/耗时更新、成功显示实际数量、重复/无效路径错误和进度事件不会提前结束请求。

### 8.3 性能测量

使用相同硬件、相同模型和相同预处理，分别测量 1+1、5+10、10+15、超过 30 张时：

- 建库耗时（从请求进入到最终响应）；
- 单张预测耗时及模板总数增加后的平均耗时；
- GPU 显存/系统内存峰值（若运行环境可采集）。

报告实际测量值，不以理论值替代。预期建库特征提取成本随图片数近似线性增长，预测候选比较成本随模板数增长；模型和融合阈值不变。

## 9. 风险与回滚

- 大模板库会增加首次建库时间、磁盘占用和缓存内存；Qt 只提醒，不擅自限制用户。
- 进度事件是可选增强，最终响应仍是完成判定，保证旧客户端兼容。
- 若进度协议实现出现问题，可关闭进度发送而保留动态模板核心逻辑；磁盘 manifest 与恢复规则保持向后兼容。

## 10. 完成定义

只有当生产代码、Qt 文案、协议和测试中不再存在“必须正好 5 张”的运行时限制，所有验收场景通过，现有测试不回归，并完成耗时报告后，本变更才算完成。
