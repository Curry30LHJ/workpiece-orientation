# 动态正反面模板数量设计

## 1. 背景与目标

当前工件库把正面和反面模板固定为各 5 张。该限制会造成两类问题：一方面少量样本无法快速验证，另一方面当某一面需要更多视角或更多遮挡变化样本时，用户选择的图片无法全部进入缓存。

本变更将模板数量改为“每面任意正整数、正反面数量可不同”，并保证选中的每一张有效图片都会写入工件库并参与预测。旧版本已经建立的 5+5 工件库不需要迁移即可恢复。

## 2. 范围与不变项

### 2.1 本次包含

- Python 后端的建库校验、缓存生成、预测遍历和工件库恢复。
- TCP 建库请求的参数校验，以及建库过程进度事件。
- Qt 模板多选、数量提示、低样本提醒、建库进度/耗时和完成结果。
- 覆盖等数量与不等数量模板的单元测试、协议测试、Qt 测试和旧库恢复测试。
- 建库与预测耗时的数量扩展测量。

### 2.2 本次不包含

- 不修改 PP-ShiTuV2、ALIKED、LightGlue、局部/全局融合阈值或特征提取模型。
- 不增加训练、微调或新模型依赖。
- 不改变已有的图像预处理、候选评分和最终判定逻辑；仅改变候选模板集合的数量。
- 离线基准脚本为保证实验可复现而设置的样本数属于实验参数，不属于生产建库规则；生产建库代码和 Qt 文案中不得保留“必须正好 5 张”的限制。

### 2.3 核心不变量

- `len(front_images) > 0` 且 `len(back_images) > 0` 是唯一的数量下限；不存在数量上限，也不存在正反面数量相等的要求。
- 对一次成功建库，源列表、磁盘模板、全局向量和局部特征在每个标签下的数量必须完全相等。
- 模板顺序可以影响存储编号，但不得影响是否参与预测；预测必须访问两个标签下的全部缓存候选。
- 任何校验或特征构建失败都不得留下新库、半成品库或覆盖失败后的残缺旧库。

## 3. 数据模型与兼容性

### 3.1 模板缓存

`TemplateCache` 按标签保存完整集合：

- `global_vectors["front"]` 和 `global_vectors["back"]` 的第一维分别等于正面、反面实际模板数；
- `local_features["front"]` 和 `local_features["back"]` 分别保存同样数量的局部特征；
- 预测时对每个标签的全部候选执行现有全局/局部评分，取现有规则下的最佳结果；不使用固定下标、固定循环次数或固定 5 张假设。
- 局部特征继续常驻 CPU。预测时逐个将候选移到 GPU、完成匹配后再处理下一个候选，不一次性构造全部 GPU 候选列表；这只降低峰值显存，不改变候选集合、得分算法或融合阈值。

### 3.2 manifest

新建库的 `manifest.json` 增加实际数量字段：

```json
{
  "schema_version": 1,
  "id": "...",
  "name": "...",
  "labels": {"0": "front", "1": "back"},
  "template_counts": {"front": 5, "back": 12},
  "created_at": "..."
}
```

恢复时：

1. 如果存在 `template_counts`，要求 `front`、`back` 都是正整数，并校验它与磁盘上两个标签目录中的实际有效图片数一致；字段格式错误或数量不一致均视为损坏并跳过该库。
2. 如果没有 `template_counts`，按旧版本行为从 `0/`、`1/` 目录枚举并校验图片，数量由目录内容推导。因此旧版 5+5 库继续兼容，且不把 5 当作新规则。

`schema_version` 仍为 1，因为新增字段是向后兼容的可选字段。模板文件按用户选择顺序逐一复制；不按数量切片、不截断、不丢弃。文件编号宽度根据该面的模板总数计算，至少为两位，例如 8 张使用 `00`～`07`，101 张使用 `000`～`100`，从而保证恢复时按文件名排序仍与选择顺序一致。

## 4. 校验规则

建库前后端均执行必要校验，后端是最终可信边界：

- 正面和反面列表都必须是列表，且长度均为正整数；两面数量可以不同；不设置最大数量。
- 每个元素必须是字符串路径；任何非字符串元素直接拒绝请求，不再静默过滤。
- 每个路径必须指向支持的图片扩展名、普通文件且可被图像读取器读取。
- 同一面及正反面之间都不得出现重复图片。以下任一条件成立即视为重复：解析后的规范化路径相同（Windows 下忽略大小写），或成功解码后的像素尺寸、类型和内容完全相同。这样即使同一图片被复制成不同文件名，也不会同时进入模板库。
- 空列表、无效路径、不可读图片、重复图片返回明确错误，且不创建半成品工件库。
- 当正反面模板总数大于 30 张时，Qt 显示“模板较多，建库和检测耗时可能增加”的性能提醒；该阈值只控制提示，不参与后端校验，也不构成最大数量。
- Qt 在任一面少于 3 张时显示黄色提示，但仍允许用户建库；数量显示使用实际值，不出现“/5”或“正好 5 张”。
- “不拒绝数量过多”指不设置业务数量上限。磁盘写满、系统内存不足或模型执行失败属于运行故障，必须返回明确错误并回滚事务，不能被包装成数量校验错误或静默成功。

## 5. 建库进度协议

为了让 Qt 能显示真实进度，Qt 在建库请求中显式加入 `progress_events: true`。只有请求选择该能力时，后端才会在最终响应前发送同一 `request_id` 的进度事件；未提供该字段或值为 `false` 时仍保持一请求一响应，兼容已有客户端。

请求示例：

```json
{
  "version": 1,
  "request_id": "...",
  "command": "register",
  "name": "M1",
  "front_images": ["..."],
  "back_images": ["..."],
  "replace": false,
  "progress_events": true
}
```

进度事件示例：

```json
{
  "version": 1,
  "request_id": "...",
  "event": "progress",
  "command": "register",
  "progress": {
    "phase": "features",
    "label": "front",
    "completed": 7,
    "total": 17,
    "elapsed_ms": 842
  }
}
```

约定：

- `phase` 只使用 `validating`、`copying`、`features`、`committing`。`total` 始终为正反面模板数之和；`completed` 表示已完成特征缓存的模板数，在前两个阶段为 0，在 `features` 阶段按图片从 1 单调递增到 `total`，提交阶段保持为 `total`。
- 后端在阶段切换和每张模板完成校验、复制或特征缓存时发送活动事件。Qt 的进度条在校验/复制时显示当前阶段，在特征阶段显示 `completed/total`。
- 进度事件不是最终响应，因此不携带 `ok`；`BackendClient` 必须先识别 `event == "progress"`，再进入现有最终响应的 `ok` 分支。
- `BackendClient` 收到合法进度事件时只发出进度信号，不清除待处理请求；同时重新启动 `request_timeout_ms` 计时器，使它表示“后端无活动超时”，而不是整个建库的总时限。收到最终成功或失败响应后才结束请求。
- 进度事件必须与当前待处理请求的 `request_id` 和 `command` 一致；字段缺失、越界或请求不匹配均按协议错误处理。
- 未选择 `progress_events` 的旧客户端只会收到最终响应。最终响应格式保持兼容，并额外返回 `template_counts` 和 `elapsed_ms`。
- 进度发送异常不得从通知回调传播到建库事务；连接断开后停止发送后续进度，建库仍按事务规则完成或回滚，Qt 显示连接错误。

最终成功响应中的数量必须从已经提交的 `WorkpieceRecord` 推导，不能直接回显未经验证的请求数组；`elapsed_ms` 从后端开始校验到事务提交完成为止。响应包含：

```json
{
  "ok": true,
  "workpiece": {"id": "...", "name": "..."},
  "template_counts": {"front": 5, "back": 12},
  "elapsed_ms": 1234
}
```

## 6. Python 后端设计

### 6.1 `OrientationClassifier`

移除固定数量常量和 `len(...) == 5` 检查。`build_template_cache` 的接口为两个非空路径序列和一个可选的模板完成回调；回调只暴露 `label`、已完成数和总数，不暴露 TCP/JSON 细节。函数按序读取每张图片、提取全局向量与局部特征，并在每张图片的两类特征都进入缓存后回调。已有评分函数、阈值和设备选择保持不变。

该模块仍自行拒绝任一空序列，以便直接调用和恢复路径也满足缓存不变量。预测的局部匹配改为逐候选搬运和评分，但仍对全部候选取现有最大值。

### 6.2 `WorkpieceLibrary`

将“正好 5 张”校验改为正整数校验，保留全部路径校验，并补充解码内容指纹的跨面/同面重复校验。事务暂存目录复制所有模板，manifest 写入实际数量，缓存构建失败时回滚。恢复流程使用第 3 节的 manifest 兼容规则。

`register` 接收可选的领域进度回调并负责阶段编排；传给缓存构建器的内部回调只负责把单张模板完成事件转换为整体进度。这样 `WorkpieceLibrary` 的接口隐藏事务、文件编号和阶段管理，TCP 层只负责把领域进度序列化。恢复调用不发送建库进度，但会使用实际模板数量重建全部缓存。

### 6.3 TCP 服务

注册请求不再使用列表过滤表达式；列表中出现非字符串即返回 `INVALID_REQUEST`。`progress_events` 如果存在则必须是布尔值。dispatcher 和 TCP server 仅在显式启用时创建进度适配器，最终响应附带实际数量与耗时。其它命令、模型和阈值不变。

## 7. Qt 界面设计

- 两个模板按钮均使用 `QFileDialog::getOpenFileNames`，不限制选择数量；对话框标题不含固定数字。
- 状态文本分别显示“正面已选择 N 张”和“反面已选择 M 张”。任一面为 1～2 张时显示“模板较少，建议补充更多角度，但仍可建库”；总数大于 30 张时显示性能提醒。两类提醒都不禁用建库按钮。
- 点击建库后禁用重复提交，显示总数、当前阶段、`QProgressBar` 和已耗时；进度来自 TCP 事件，耗时使用界面侧单调计时器实时刷新。
- 成功后显示后端返回的实际正面/反面数量和总耗时；失败后停止计时并保留可重试状态。
- 路径规范化必须保持列表顺序和元素数量，不做静默去重或空值过滤；重复图片由校验流程明确提示并阻止建库。
- 建库请求固定携带 `progress_events: true`。Qt 处理进度事件时不得把 `BackendClient` 从 Busy 提前切回 Ready，也不得允许第二个请求并发进入。

## 8. 测试计划与验收标准

### 8.1 Python 单元/集成测试

至少覆盖：

| 场景 | 期望 |
| --- | --- |
| 1+1 | 建库成功，manifest/cache 为 1、1，预测遍历两张模板 |
| 5+10 | 建库成功，数量不相等且全部文件存在并参与预测 |
| 10+15 | 建库成功，恢复后数量仍为 10、15 |
| 总数 31 张及 31+31 | 产生性能提醒但建库成功，不截断 |
| 101+1（轻量假缓存） | 建库成功，编号排序与选择顺序一致，证明两位编号不是隐式上限 |
| 空列表 | 拒绝，库目录不落盘 |
| 非字符串/不存在/不可读图片 | 拒绝，不静默忽略 |
| 同面重复、跨面重复、不同路径但解码内容相同 | 拒绝 |
| 旧版无 `template_counts` 的 5+5 manifest | 恢复成功 |
| 新版 manifest 数量字段格式错误或与磁盘不一致 | 跳过损坏工件库，不建立缓存 |
| 预测缓存数量 | 只依赖实际集合长度，不依赖常量 5 |
| 未选择进度事件 | 只返回一个最终响应，保持旧客户端兼容 |
| 选择进度事件 | 阶段合法、`completed` 非递减，最终响应包含数量和耗时 |

### 8.2 Qt 测试

验证任意多选、正反面不等数量显示、少量/大量提示、进度/耗时更新、成功显示实际数量、重复/无效路径错误，以及进度事件不会提前结束请求并会刷新无活动超时。

### 8.3 性能测量

自动化测试只断言调用次数、缓存数量和候选遍历，不断言绝对毫秒数，避免把机器性能波动当作功能回归。性能报告使用相同硬件、相同模型、相同预处理和相同测试图片，分别测量 1+1、5+10、10+15、31+31：

- 建库耗时（从请求进入到最终响应）；
- 单张预测耗时：先预热，再连续运行至少 5 次并报告中位数；
- GPU 显存/系统内存峰值（若运行环境可采集）。

报告实际测量值、硬件和模板总数，不以理论值替代，也不对不同机器的绝对耗时作横向结论。预期建库特征提取成本随图片数近似线性增长，预测候选比较成本随模板数增长；模型和融合阈值不变。

## 9. 风险与回滚

- 大模板库会增加首次建库时间、磁盘占用和缓存内存；Qt 只提醒，不擅自限制用户。
- 大模板库也会增加后端启动时的恢复耗时，因为缓存需要从磁盘重新构建；继续复用现有“模型加载中”状态，不在本变更中增加持久化特征格式。
- 进度事件由请求显式选择，最终响应仍是完成判定，未选择进度的旧客户端保持一请求一响应。
- 若进度协议实现出现问题，可关闭进度发送而保留动态模板核心逻辑；磁盘 manifest 与恢复规则保持向后兼容。

## 10. 完成定义

只有当生产代码、Qt 文案、协议和测试中不再存在“必须正好 5 张”的运行时限制，所有验收场景通过，现有测试不回归，并完成耗时报告后，本变更才算完成。
