# Windows 完全离线 GPU/CPU 双版本便携包设计

日期：2026-08-28

基础分支：`feature/20260827/lightweight-geometry-fast-path`

## 1. 背景

当前系统由 Qt 5.14.2 桌面程序和 Python 推理后端组成。开发环境依赖 Conda、Paddle/PaddleClas、OpenCV、Qt 动态库以及本机绝对路径，尚不能直接复制到甲方电脑运行。

本次交付需要将当前已验收的 `fast_geometry` 推理流程制作成两个相互独立的 Windows 10/11 64 位免安装压缩包：

- NVIDIA GPU 版；
- 纯 CPU 版。

两个版本都必须完全离线运行，不要求甲方安装 Python、Conda、Qt 或 CUDA Toolkit。GPU 版只允许把兼容的 NVIDIA 显卡驱动作为外部前置条件。交付包不携带开发阶段已经建立的工件库和几何规则。

## 2. 已确认决策

1. 采用“Qt 主程序 + 独立后端 EXE”的 `onedir` 便携结构，不采用单文件自解压 EXE。
2. GPU 版和 CPU 版分别构建、分别压缩、分别验收。
3. 用户只启动 Qt 主程序；Qt 静默启动和关闭后端，不显示命令行窗口。
4. 两个版本使用完全相同的数据格式，整个 `data` 目录可以相互迁移。
5. 交付包中不出现可直接查看的 `.py` 源文件；本次不增加加密、授权码或机器绑定。
6. GPU 版继续以当前 RTX 4060 Ti 验证机上的预热单图后端 `P95 <= 25 ms` 为性能门禁。
7. CPU 版保证功能和识别逻辑一致，但不承诺 25 ms；必须报告实测性能。
8. 交付形式为两个完全离线的免安装 ZIP。

## 3. 目标

1. 在未安装 Python、Conda、Qt 和 CUDA Toolkit 的干净 Windows 10/11 x64 电脑上，解压后即可运行。
2. 用户只需双击一个 Qt 主程序，后端生命周期由 Qt 自动管理。
3. 程序、模型与用户数据隔离；升级程序时保留 `data` 即可保留现场数据。
4. GPU/CPU 版本的数据格式、业务功能、算法配置和识别结果契约保持一致。
5. 发布包不依赖开发机绝对路径、环境变量或当前工作区文件。
6. 发布包不携带现有工件库、模板、几何规则、测试图片、运行报告或开发日志。
7. 保持 PP-ShiTu、轻量几何规则、每工件 Ridge 判别头和现有融合阈值不变。
8. 构建、依赖收集、内容审计和验收可以通过脚本重复执行。

## 4. 非目标

- 不制作 MSI/NSIS 等安装程序。
- 不制作单文件自解压程序。
- 不实现在线更新。
- 不实现授权码、机器绑定或强防逆向保护。
- 不重新训练或微调模型。
- 不修改现有识别决策、几何规则语义或阈值。
- 不恢复生产在线路径中的 ALIKED、LightGlue 或 ORB。
- 不承诺 CPU 版达到 `P95 <= 25 ms`。
- 不把当前工件库或当前几何规则作为示例数据交付。
- 不在本次增加完整的数据管理新页面；跨版本迁移以复制 `data` 目录并执行启动校验为主。

## 5. 交付物与目录结构

最终产出：

- `WorkpieceOrientation-GPU-x64-{version}.zip`；
- `WorkpieceOrientation-CPU-x64-{version}.zip`；
- 与每个 ZIP 对应的 SHA-256 文件；
- 中文使用说明；
- 兼容性、功能和性能验收报告；
- 第三方组件及许可证清单。

其中 `{version}` 必须由本次构建的正式版本号替换，并与 `version.json` 完全一致，不能以未展开的占位符出现在实际交付文件名中。

两个 ZIP 解压后的逻辑结构一致：

```text
WorkpieceOrientation-<edition>/
├─ WorkpieceOrientation.exe
├─ app_config.json
├─ qt.conf
├─ Qt5Core.dll 等 Qt/MSVC 运行组件
├─ platforms/、imageformats/ 等 Qt 插件
├─ backend/
│  ├─ orientation_backend.exe
│  └─ runtime/                    后端私有依赖
├─ models/
│  └─ shitu_rec/                  PP-ShiTu 推理模型
├─ data/
│  ├─ workpieces/
│  ├─ rules/
│  ├─ cache/
│  ├─ logs/
│  └─ temp/
├─ version.json
├─ third_party_licenses/
└─ 使用说明.txt
```

物理文件可以根据 Qt 和 PyInstaller 的加载约束分布在相邻子目录中，但用户入口、`data` 边界和上述逻辑层级不得改变。`WorkpieceOrientation.exe` 是唯一面向普通用户的启动入口，`orientation_backend.exe` 不要求用户手工运行。

## 6. 路径和数据边界

### 6.1 根目录解析

发布模式以 Qt 可执行文件所在目录为唯一程序根目录，禁止使用当前工作目录推断资源位置。所有资源路径从程序根目录解析并规范化：

- 后端：`backend/orientation_backend.exe`；
- 模型：`models/shitu_rec`；
- 配置：`app_config.json`；
- 可写数据：`data`。

开发模式继续允许显式配置 Python 解释器和后端脚本，但发布配置不得包含开发机路径。程序必须支持根目录含中文、空格和较长路径。

### 6.2 只读和可写内容

程序、后端运行库和模型视为只读；所有运行时写入统一进入 `data`：

- 工件模板、manifest、派生快速缓存和 Ridge 判别头进入 `data/workpieces` 或现有库结构对应位置；
- 几何规则及修订进入 `data/rules` 或工件库的版本化规则位置；
- 日志进入 `data/logs`；
- 临时文件进入 `data/temp`。

日志按日期滚动并设定总容量上限。临时文件正常退出时清理，异常残留在下一次启动时清理。禁止把运行日志、缓存或用户图片写入 `backend`、`models` 或 Qt 插件目录。

### 6.3 空数据交付

构建暂存区必须从空目录创建，不能直接复制开发环境的 `data`。交付时：

- `data/workpieces` 为空；
- 不存在已发布或草稿几何规则；
- 不存在确认入库图片、回收站数据、批量检测结果或运行缓存；
- 第一次启动自动创建所需目录和空库元数据；
- 空库是正常状态，界面显示“尚未建立工件库”，不得当作后端故障。

## 7. GPU/CPU 设备配置

后端增加显式且可验证的设备配置，不再在分类器内部硬编码 `use_gpu=True`。

### 7.1 GPU 版

- 发布配置固定 `compute_device=gpu`；
- 发布配置固定 `inference_mode=fast_geometry`，不接受未随包交付依赖的旧推理模式；
- Paddle 启用 GPU，MKLDNN 关闭；
- 携带与构建版本匹配且允许再分发的 CUDA/cuDNN/Paddle 动态组件；
- 外部只要求兼容的 NVIDIA 显卡和驱动；
- 启动时验证 Paddle 实际设备、GPU 可见性和一次最小推理；
- GPU 不可用或版本不兼容时拒绝进入“已连接”，不得静默回退 CPU。

GPU 功能兼容范围以交付报告列出的 Paddle、CUDA 运行时和驱动要求为准。`P95 <= 25 ms` 只对当前 RTX 4060 Ti 验证机及约定数据和口径成立；甲方使用不同 GPU 时必须记录该机器的独立实测结果。

### 7.2 CPU 版

- 发布配置固定 `compute_device=cpu`；
- 发布配置固定 `inference_mode=fast_geometry`，不接受未随包交付依赖的旧推理模式；
- 使用 Paddle CPU 包并启用 MKLDNN；
- 不加载 CUDA DLL，不探测或等待 NVIDIA GPU；
- 在无独立显卡的干净环境完成启动与推理验收。

两个版本必须返回相同的业务字段和方向标签。浮点实现差异导致的个别结果差异必须在固定验收集上对比并报告，不能以“设备不同”为由静默接受。

## 8. Qt 与后端生命周期

### 8.1 启动状态机

一次启动代次内的状态单向推进：

```text
Stopped
  -> StartingProcess
  -> LoadingRuntime
  -> LoadingModel
  -> RestoringLibrary
  -> Ready

任一阶段 -> Failed
```

Qt 启动后端时使用隐藏窗口模式。后端通过结构化就绪响应报告阶段、进度、设备、版本和最近错误。单纯端口可连接不等于模型已就绪，只有完成模型加载、设备自检和工件库恢复后才能进入 `Ready`。

同一启动代次中，迟到的探测结果不得把新状态覆盖为旧状态，从而避免界面在“未连接”和“加载中”之间跳变。开发配置仍可按 GPU 30 秒、CPU 60 秒设置启动超时；便携包生成配置统一使用 600000 ms（10 分钟）看门狗上限，因为离线冻结后的 Paddle 首次初始化在验证机上约需 78 秒，客户机首次启动可能更慢。该值只是超时上限，不是固定等待时间；后端会持续报告加载阶段，成功后立即进入 `Ready`，超时则显示阶段、日志位置和可操作错误。

### 8.2 进程所有权

- Qt 只终止由本次 Qt 实例启动且身份令牌匹配的后端进程；
- 端口已占用时，先验证服务名、协议版本和实例身份，不得结束未知进程；
- 重复点击启动或重启不能产生多个后端；
- 正常退出先请求后端优雅关闭，超时后只强制结束本实例持有的进程；
- Qt 崩溃后的孤儿后端由实例锁和父进程监测退出，下一次启动可以安全恢复。

### 8.3 开发与发布模式

Qt 后端管理器支持两个明确模式：

- 开发模式：按显式配置启动 Python 解释器和后端脚本；
- 发布模式：按相对路径启动 `orientation_backend.exe`。

发布包固定为发布模式。Qt 读取配置后缓存本次启动配置；若用户修改需要重启的高级配置，界面必须明确提示“请退出并重新打开整个程序”，不能只重启后端造成旧配置继续生效。

## 9. 后端打包设计

后端使用 PyInstaller `onedir` 构建。`orientation_backend.exe` 与其私有运行文件放在 `backend` 内，避免污染 Qt 根目录。

构建采用显式入口、显式资源和显式依赖清单：

- 收集 Paddle/PaddleClas、NumPy、OpenCV 及 `fast_geometry` 正式路径所需模块；
- 收集 Paddle 推理引擎、MKL/MKLDNN 或 GPU 运行时所需动态库；
- 收集运行时读取但不能由静态导入发现的 PaddleClas 配置和资源；
- 模型作为外部只读资源放入 `models`，不嵌入 EXE；
- 排除测试、基准、训练、开发工具、Torch、ALIKED、LightGlue 及旧局部匹配入口；OpenCV 仍作为正式依赖保留，但生产请求不得执行 ORB 局部匹配；
- 禁止把整个 Conda 环境无选择复制进交付包。

PyInstaller 的目的为离线分发和避免直接交付 `.py`，不宣称提供强加密或不可逆防护。

## 10. Qt 打包设计

Qt 5.14.2 以 Release 模式构建，通过 `windeployqt` 和显式白名单收集：

- Qt Core、Gui、Widgets、Network 等实际使用模块；
- Windows 平台插件；
- 实际支持图片格式所需插件；
- 应用本地 MSVC 运行组件。

部署后执行依赖扫描和空 PATH 启动测试。不能依赖 Qt 安装目录、开发者 PATH 或系统全局 VC++ Redistributable。未使用的 Qt 模块和插件不随包携带。

## 11. 构建流水线

GPU 和 CPU 使用两个干净、独立、固定版本的构建环境。流水线按以下顺序执行：

1. 验证工作树、版本号、模型指纹和构建工具版本；
2. 在全新的暂存目录构建 Qt Release；
3. 分别构建 GPU 或 CPU 后端；
4. 收集 Qt、MSVC、Paddle 和设备运行依赖；
5. 复制 PP-ShiTu 模型并校验模型文件指纹；
6. 生成对应版本的发布配置；
7. 创建空 `data` 结构；
8. 生成 `version.json`、第三方许可证和内容 manifest；
9. 执行发布包静态审计与动态冒烟测试；
10. 生成 ZIP 和 SHA-256；
11. 在干净 Windows 环境完成最终验收。

构建脚本必须失败而不是忽略以下问题：缺失动态库、模型指纹错误、出现绝对开发路径、出现 `.py`、出现用户工件数据、GPU/CPU 配置与依赖不一致，或冒烟测试失败。

## 12. 数据兼容、迁移与升级

### 12.1 统一格式

GPU 和 CPU 使用同一工件库 schema、几何规则 schema 和快速缓存 schema。设备相关信息不能写入不可迁移的事实数据。可以重建的推理缓存必须带模型、预处理、算法和设备无关特征版本指纹。

如果某类派生缓存确实与设备实现相关，迁移后将其标记为过期并后台重建，而不是拒绝加载整个工件库。

### 12.2 复制式迁移

基础迁移方式是：退出程序，把完整 `data` 目录复制到一个新解压且目标 `data` 为空的版本，再启动目标版本。目标已有业务数据时禁止目录合并和静默覆盖；用户必须先完整备份并选择保留其中一套数据。本次不实现两个工件库的自动合并。启动时校验：

- 数据 schema；
- manifest 完整性；
- 工件库和规则修订关系；
- 模型/预处理指纹；
- 缓存是否需要重建。

本次不新增复杂的数据管理页面。使用说明给出复制步骤；程序在启动时完成导入校验并在迁移前创建带时间戳的备份。迁移采用临时目录和原子切换，失败时保留原始数据并给出恢复位置。

### 12.3 升级

程序升级以替换除 `data` 外的文件为主。新版本首次读取旧数据时：

1. 识别 schema 版本；
2. 需要迁移时先备份；
3. 在临时位置完成迁移和校验；
4. 成功后原子切换；
5. 失败则继续保留旧数据并拒绝危险写入。

旧 5+5 工件库、任意正整数模板数以及正反模板数量不同的工件库继续兼容。

## 13. 日志与错误提示

发布模式必须把 Python 异常转换为稳定的错误码和中文说明，至少覆盖：

- 后端文件缺失或无法启动；
- Qt 或后端依赖缺失；
- 模型缺失或指纹错误；
- GPU 不可用、驱动不兼容或 Paddle 未实际使用 GPU；
- CPU 运行库初始化失败；
- 数据目录不可写；
- 数据迁移或恢复失败；
- 端口被未知程序占用；
- 后端启动超时；
- 工件库为空；
- 快速缓存构建失败。

“工件库为空”是正常业务状态，不显示为红色后端故障。错误提示需包含下一步操作和日志目录，日志不得记录模板图片内容或不必要的个人路径。

## 14. 内容与安全审计

每次构建自动检查：

- 不存在 `.py`、`.pyi`、测试脚本或源代码目录；
- 不存在 `E:\\Project`、Conda 环境路径、开发用户名等绝对路径残留；
- 不存在 `pytest`、manual、runtime report、测试图片或基准数据；
- 不存在当前 `data`、工件 ID、模板或几何规则；
- GPU 包不包含 CPU 配置，CPU 包不包含 CUDA 依赖或 GPU 配置；
- 所有 EXE 和 DLL 的导入依赖都能在包内或 Windows 系统目录解析；
- manifest 中每个交付文件具有相对路径、大小和 SHA-256；
- 第三方组件均有版本和许可证记录。

压缩包不是安全边界。基础源码隐藏只防止直接浏览 `.py`，不保证无法逆向。

## 15. 测试设计

### 15.1 单元测试

- 程序根目录不受当前工作目录影响；
- 中文、空格和长路径正确解析；
- GPU/CPU 配置生成正确且互斥；
- GPU 配置不能静默回退 CPU；
- CPU 配置不触发 CUDA 初始化；
- 发布模式启动后端 EXE，开发模式仍可启动 Python 脚本；
- 启动代次能丢弃迟到探测结果，状态不回退跳变；
- Qt 只关闭自己持有的后端进程；
- 空数据目录可初始化；
- 日志轮转和临时目录清理遵守容量与目录边界；
- 数据迁移先备份、成功原子切换、失败保留原始数据；
- 旧 5+5 和正反数量不同的工件库均可恢复；
- 包内容审计能拒绝源码、绝对路径和现有工件数据。

### 15.2 集成测试

两个版本分别验证：

- 双击 Qt 后自动启动后端且无控制台窗口；
- 启动状态依次推进到就绪，不反复跳变；
- 空库启动、建库、任意数量模板、单张检测、批量检测、确认入库、删除、规则管理和重启恢复；
- 退出、重启和后端崩溃恢复不遗留重复进程；
- 程序目录断网运行；
- `data` 从 GPU 复制到 CPU、再复制回 GPU 后可恢复；
- 程序目录含中文和空格时完整业务流程可用。

### 15.3 干净环境验收

最终验收环境不得安装 Python、Conda、Qt 或 CUDA Toolkit：

- GPU 环境只预装兼容 NVIDIA 驱动；
- CPU 环境无 NVIDIA GPU 依赖；
- PATH 中不包含开发工具或构建环境；
- 测试网络断开时启动和业务流程；
- 使用打包后的 ZIP 解压产物，而不是暂存目录。

## 16. 性能和准确率验收

### 16.1 GPU 版

- 硬件：当前 RTX 4060 Ti 验证机；
- 使用与快速推理正式验收一致的数据集和统计口径；
- 模型和工件库加载完成后预热 50 次；
- 连续运行至少 1000 次单图检测；
- 后端完整检测耗时 P95 必须 `<= 25 ms`；
- 同时报告 mean、P50、P99 和 max；
- Qt 端到端耗时单独报告；
- 固定验收集不得低于当前 `fast_geometry` 准确率基线。

性能验收使用外部验收数据，数据不得进入交付 ZIP。

### 16.2 CPU 版

- 记录 CPU 型号、核心数、内存和 Windows 版本；
- 确认 MKLDNN 实际启用；
- 运行同一固定验收集；
- 报告准确率及相对 GPU 版的所有结果差异；
- 报告 mean、P50、P95、P99 和 max；
- 不设 25 ms 硬门禁，但不得隐藏或缩小测试范围。

### 16.3 启动耗时

- 开发配置 GPU 版默认 30 秒、CPU 版默认 60 秒内达到 `Ready`；
- 便携包 GPU/CPU 版使用 600000 ms（10 分钟）启动看门狗上限，并记录实际 Ready 耗时；
- 分别报告进程启动、运行库加载、模型加载和工件库恢复耗时；
- 超时必须停止等待并给出当前阶段和可操作提示。

## 18. 实施边界与顺序

实现应从当前快速路径分支创建独立的离线打包功能分支，避免把交付基础设施和算法开发混在一个未审查提交中。

建议顺序：

1. 固定根目录、数据目录和设备选择契约并补测试；
2. 实现后端 EXE 启动和稳定就绪状态机；
3. 实现 GPU/CPU 两套后端构建；
4. 实现 Qt/MSVC 离线部署；
5. 实现空数据暂存、内容审计、manifest 和许可证生成；
6. 实现数据迁移校验与备份；
7. 运行自动化测试、干净环境冒烟和完整业务验收；
8. 运行 GPU 性能门禁和 CPU 性能报告；
9. 生成两个 ZIP、SHA-256、使用说明和验收报告。

## 19. 验收标准

本功能只有同时满足以下条件才算完成：

1. 两个 ZIP 均能在对应的干净、断网 Windows 环境解压即用；
2. 用户只启动 Qt，后端静默启动并由 Qt 正确关闭；
3. 后端状态稳定，不再在未连接和加载中之间反复跳变；
4. GPU 版只依赖兼容 NVIDIA 驱动，CPU 版不依赖 NVIDIA；
5. GPU 版在 RTX 4060 Ti 上达到约定的 `P95 <= 25 ms`；
6. CPU 版提交完整、可复现的性能报告；
7. 固定验收集准确率不低于当前快速模式基线，CPU/GPU 差异已报告；
8. 两版本完整支持建库、检测、批量检测、确认入库、删除和几何规则管理；
9. 两版本的 `data` 可以相互迁移，失败迁移不会破坏原数据；
10. 交付包不含当前工件库、当前规则、测试数据、开发日志、`.py` 或开发机绝对路径；
11. 模型、算法、几何规则语义、Ridge 判别和现有阈值未被修改；
12. 自动化测试、包内容审计、依赖扫描和干净环境冒烟全部通过；
13. 两个 ZIP 均提供 SHA-256、版本清单、中文说明和第三方许可证。
